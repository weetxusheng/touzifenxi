# 项目开发规范

本文档用于约束 `/Users/xusheng/Documents/project/touzifenxi` 的持续开发方式。目标不是补一份“写给自己看的说明”，而是建立一套后续可以稳定复用、稳定交接、稳定打包 skill 的统一规范。

当前优先约束两个方向：

1. Python 代码开发规范
2. Skill 设计、目录与分发规范

后续新增模块、脚本、skill、提示词、测试时，默认都应遵守本文档；如果需要例外，先在对应文档里显式说明原因。

配套文档：

- `AGENTS.md`
- `docs/development-workflow.md`
- `docs/skill-packaging.md`

## 1. 总体原则

- 先区分“项目通用能力”和“单个 skill 的分发能力”，不要把两者混写。
- 先保证目录和边界清晰，再补功能；不要靠临时脚本堆出长期能力。
- 先把需求对应的主场景、边界场景、失败场景和 fallback 用例列清，再进入实现。
- 原始数据、分析结果、简报、状态文件分目录存放，不混放。
- 能复用的逻辑进 `src/`，只服务单个 skill 的提示词、脚本、配置放进对应 `skills/` 目录。
- 文档优先写清“职责边界”和“输入输出”，不要写成流水账。

## 2. 顶层目录规范

项目顶层目录职责固定如下：

- `src/touzifenxi/`
  - 项目级 Python 包
  - 只保留平台级与多 skill 可复用能力
- `skills/`
  - 每个可分发 skill 的独立目录
  - 放 skill 自身文档、配置、提示词、运行脚本、私有运行代码和输出骨架
- `tests/`
  - 项目级测试
  - 统一管理平台测试、治理测试和各 skill 的模块测试
- `data/raw/`
  - 原始抓取结果
  - 允许 CSV、JSON、HTML 快照等原始或近原始数据
- `data/processed/`
  - 经过清洗、归一、结构化后的中间结果
- `reports/`
  - 面向阅读的简报、搜索清单、日报等输出
- `state/`
  - 本地运行状态、SQLite、缓存状态等
- `build/`
  - 打包产物
  - 例如 skill zip、临时构建结果
- `docs/`
  - 项目说明、架构文档、数据库说明、开发规范

约束：

- 不要把提示词、配置、模板散落到 `docs/`、仓库根目录或个人目录。
- 不要把临时调试脚本长期放在仓库根目录。
- 不要把 `build/` 下生成内容视为源码来源。

### 2.1 目录命名与自说明规则

- 顶层长期目录优先使用稳定英文名，不使用临时中文名或个人缩写。
- 会长期沉淀内容的目录，默认补一个简短 `README.md` 或专用说明文件，至少写清：
  - 目录用途
  - 推荐放哪些文件
  - 不应放哪些文件
- `reports/`、`data/`、`tests/` 这类会持续增长的目录，必须通过子目录分层，避免所有文件平铺在一级目录。
- 运行目录必须使用可排序命名，例如：
  - `c114_search_YYYYMMDDHHMM`
  - `c114_range_YYYYMMDD_YYYYMMDD_<timestamp>`
- 默认不保留历史兼容脚本；若确有必要，必须限时存在并在对应 skill 的 `SKILL.md` 中明确标记“兼容入口”。

## 3. Python 开发规范

### 3.1 模块职责

- `src/touzifenxi/` 内的模块应该是“可复用能力模块”，而不是一次性命令堆叠。
- 单个文件只负责一个清晰主题，例如：
  - 抓取
  - 解析
  - 存储
  - CLI 编排
  - 报告生成
- 若一个文件同时承担“抓取 + 解析 + 落盘 + CLI 参数处理”，应优先拆分。

推荐分层：

1. `client / fetch`
   - 负责网络请求
2. `parser / extractor`
   - 负责 HTML、文本、元信息提取
3. `service / pipeline`
   - 负责业务编排
4. `storage / exporter`
   - 负责 CSV、JSON、数据库、Markdown 输出
5. `cli`
   - 负责参数入口与调用编排

### 3.2 类型与数据结构

- 新增公共函数必须尽量补全类型标注。
- 优先使用 `dataclass` 表达结构化数据。
- 函数返回值要稳定，不要同一个函数有时返回 `dict`，有时返回 `list`，有时返回 `None`。
- 面向外部模块暴露的结构，优先定义成明确的数据类，而不是匿名字典。

### 3.3 函数设计

- 小函数优先，函数只做一件事。
- 函数名使用动词短语，表达真实意图，例如：
  - `fetch_text`
  - `parse_publish_date`
  - `save_reports_to_csv`
- 避免“万能函数”，例如一个函数同时负责下载、解析、筛选、打印。
- 参数要表达业务语义，不要滥用布尔开关。

### 3.3.1 场景与用例先行

- 任何新增需求、流程改造、批量化、容错、模型接入或路由调整，在编码前都必须先列清最小用例集。
- 最小用例集至少应覆盖：
  - 主流程场景
  - 边界场景
  - 失败场景
  - fallback 或降级场景
- 没有形成最小用例集前，不进入实现；不要边写边猜边补规则。
- 若需求涉及外部接口、批量任务、并发、重试、回退、结构化输出，必须提前写清“理想返回”“部分缺失”“空返回”“超时/限流”“结构不合法”这些场景。
- 完成实现后，必须逐条对照上述用例执行验证；若暂时无法自动化，至少保留明确的人工验证命令、步骤或结果说明。

### 3.4 注释与文档字符串

- 注释只解释“为什么这么做”或“这里的边界条件”，不解释显而易见的代码动作。
- 不要写这种无信息注释：
  - `# 给变量赋值`
  - `# 循环处理数据`
- 当代码已有清晰命名时，优先删掉重复描述性注释。
- 对外入口函数、复杂解析逻辑、容易误判的抓取规则，建议补简短 docstring。

推荐：

- 用注释解释页面结构陷阱、日期误判原因、去重优先级等“非显然规则”。
- 用 docstring 说明函数输入、输出和关键约束。

最低要求：

- 每个长期维护的 Python 模块都应有模块级 docstring，说明该文件负责什么、边界在哪里。
- 每个对外入口函数都应有 docstring，至少写清输入来源、输出对象和关键副作用。
- 对复杂 provider 路由、fallback 逻辑、排序规则、路径约定，至少补一行解释“为什么”的注释。
- 对 skill 私有实现代码，除了模块级 docstring 外，还应给核心数据类、公开方法、步骤入口方法补 docstring。
- 若某个方法承载业务步骤切换、模型调用、结果落盘、重试或阻断逻辑，必须写清“输入 / 输出 / 是否落盘 / 何时中止”。
- 不允许把“代码可读，所以不写任何注释”作为 skill 的默认做法；skill 作为可分发单元，后续接手者默认不是原作者。

### 3.4.1 Skill 配置与 key 注释规则

- skill 的 `config/*.json` 若因 JSON 格式限制无法直接写注释，必须提供同目录的 `README.md` 或在 `SKILL.md` 中配套说明。
- 配置说明至少要覆盖：
  - 每个 key / 配置项是做什么的
  - 哪个步骤会用到
  - 是否为硬门槛
  - 默认值是什么
  - 关闭或缺失后会发生什么
- `runtime.example.json` 这类模板文件不得只给字段名不给解释；必须能让非作者理解如何填写。
- 凡是涉及：
  - API key
  - provider 选择
  - 模型配置
  - 步骤开关
  - 输出目录模式
  都必须在配置说明里单独解释，不能让使用者靠猜。

### 3.5 异常与容错

- 抓取相关代码优先显式处理异常，不要无声吞掉。
- 如果选择容错跳过，至少保留：
  - 失败对象
  - 失败原因
  - 是否影响全局任务
- 不要用大范围 `except Exception: pass`。
- 对“页面结构不稳定”“日期缺失”“详情页无摘要”这类情况，返回可判断状态，而不是模糊失败。

### 3.6 I/O 与输出

- 原始数据输出到 `data/raw/`
- 中间结构化数据输出到 `data/processed/`
- 可读报告输出到 `reports/`
- 构建与分发产物输出到 `build/`

不要：

- 在函数内部直接写死个人机器路径
- 把业务逻辑和 `print`/终端输出耦合
- 同一个函数同时负责生成数据和决定最终展示文案

### 3.7 CLI 规范

- CLI 命令只负责参数解析、调用服务层和汇报结果。
- 具体抓取、分析、落盘逻辑不要堆在 CLI 文件里。
- CLI 返回的终端文案以“结果摘要 + 输出路径”为主，不重复打印大段原始内容。

## 4. 测试规范

### 4.1 测试位置

- 项目级测试统一放在 `tests/`
- 正式测试统一放在项目层，例如：
  - `tests/skills/<skill-name>/`
  - `tests/platform/`
  - `tests/governance/`
- skill 目录内默认不创建 `tests/`；正式测试统一收口到项目级 `tests/skills/`

### 4.2 当前默认测试方式

当前项目统一使用 `pytest` 作为执行入口；现有部分测试仍可保留 `unittest` 风格编写，但统一由 `pytest` 收集和运行。

```bash
PYTHONPATH=src:skills/c114-daily-hot-topics/src python3 -m pytest tests/skills/c114 tests/governance/test_governance.py
```

新增测试默认直接按 `pytest` 组织，不再新增新的 `unittest` 入口约定。

### 4.3 测试内容要求

- 抓取项目优先测：
  - 链接过滤
  - 日期识别
  - 关键词提取
  - CSV/JSON 输出格式
  - skill 脚本入口行为
- 修 bug 时，先补能复现问题的测试，再修实现。
- 新增 skill 时，至少要验证：
  - 配置能读到
  - 脚本入口能跑
  - 输出路径和格式符合预期
- 功能完成后，不得只跑“能跑通的一条 happy path”；必须回到开发前列出的用例，逐条确认主流程、边界、失败与 fallback 行为。

## 5. Skill 开发规范

本项目未来会持续产出 skill，因此 `skills/` 必须按统一模板管理。

### 5.1 skill 目录结构

每个 skill 默认结构如下：

```text
skills/<skill-name>/
  SKILL.md
  agents/
  config/
  prompts/
  scripts/
  src/
  output/         # 可选
```

目录职责：

- `SKILL.md`
  - skill 总览、步骤定义、当前实现状态与维护入口
- `agents/`
  - 模型配置、agent 配置
- `config/`
  - 栏目表、映射表、运行参数等
- `prompts/`
  - 所有提示词文件
- `scripts/`
  - skill 的直接执行入口
  - 默认只保留单一正式入口脚本，不新增历史兼容脚本
- `src/`
  - 该 skill 私有的运行代码
- `output/`
  - skill 脱离项目时的默认输出目录

### 5.2 SKILL.md 规范

- `SKILL.md` 正文统一使用中文。
- Frontmatter 仍保留 `name`、`description` 等标准字段。
- `description` 只描述“什么时候使用这个 skill”，不要在一行里讲完整流程。
- 正文至少应包含：
  - 适用场景
  - 默认行为
  - 输入语义
  - 输出产物
  - 目录说明
  - 分发约束

新增硬要求：

- 只要 skill 依赖任何配置项、API key、代理环境或运行参数，`SKILL.md` 必须单独写清：
  - 哪些配置是 `step 1` 就需要的
  - 哪些配置只在后续步骤才需要
  - 哪些缺失会直接阻断执行
  - 哪些只是推荐配置，不影响最小可运行链路
- 不允许只写“请补齐配置”这种笼统描述，必须至少按步骤或按功能分组说明。
- 若 skill 支持“部分步骤先跑、后续步骤再补配置”，必须明确写出“最小可运行路径”。
- 若 skill 会受代理、SSL、公司证书链或外部网络环境影响，`SKILL.md` 必须写排障说明，不能把这类问题留给使用者猜。

### 5.3 skill 与项目代码边界

- `skills/<skill-name>/scripts/` 负责 skill 的可执行入口与编排。
- `skills/<skill-name>/src/` 负责该 skill 私有的运行代码。
- `src/touzifenxi/` 负责项目级可复用逻辑。
- 如果某段逻辑是多个 skill 都会复用，应上收进 `src/touzifenxi/`。
- 如果某段逻辑只服务单个 skill，应保留在 skill 目录内，不要伪装成项目通用模块。

关键约束：

- skill 内提示词、配置、模板必须放在 skill 自己目录下。
- 不能让 skill 依赖仓库外部的绝对路径文件。
- 如果 skill 打包后需要脱离项目运行，必须保证打包内容自身完整。

### 5.4 提示词规范

- 提示词文件统一放 `prompts/`
- 文件名使用短横线命名，例如：
  - `search-keyword-agent.md`
  - `brief-summary-agent.md`
- 提示词必须写清：
  - 输入来源
  - 输出格式
  - 约束条件
  - 禁止项
- 任何提示词都不应只存在于个人目录或 `docs/` 中。

### 5.5 skill 私有代码与配置规范

- `skills/<skill-name>/src/` 下的代码只服务当前 skill，不反向依赖项目层同名业务模块。
- `skills/<skill-name>/config/` 必须区分：
  - `*.example.*`：入库模板
  - `*.local.*`：本地配置，不入库
- skill 的 `SKILL.md` 必须写清：
  - 正式入口脚本
  - 配置文件位置
  - 正式测试位置

### 5.6 scripts 规范

- `scripts/` 中的正式入口应尽量保持薄脚本：只做参数转发和最小编排，不堆放大量业务实现。
- 一个 skill 默认只保留单一正式入口脚本；若确需多个脚本，必须各自职责清晰，不能出现历史兼容残留。

### 5.5 skill 打包规范

- 打包对象是 `skills/<skill-name>/` 目录本身。
- 打包前检查：
  - `SKILL.md` 是否存在
  - `agents/` 是否齐全
  - `config/`、`prompts/`、`scripts/` 是否引用正确
  - 是否误包含 `__pycache__`、临时文件、调试产物
- skill zip 应输出到 `build/`
- 打包前应先运行校验脚本或对应 CLI 命令

## 6. 命名规范

### 6.1 Python

- 文件名：`snake_case.py`
- 函数名：`snake_case`
- 类名：`PascalCase`
- 常量名：`UPPER_SNAKE_CASE`

### 6.2 skill

- skill 目录名：短横线风格，例如 `c114-daily-hot-topics`
- 提示词文件名：短横线风格
- 配置文件名：语义清晰，例如 `channels.json`

## 7. 产物与缓存规范

- `__pycache__/`、临时抓取文件、调试快照不属于源码。
- `build/` 中的内容是构建结果，不是开发主来源。
- 新增打包或导出逻辑时，应明确：
  - 原始数据存哪里
  - 中间结果存哪里
  - 给人看的结果存哪里
  - 分发产物存哪里

## 8. 推荐开发流程

后续新增 Python 功能或 skill，默认按下面顺序推进：

1. 先确认放在 `src/` 还是 `skills/`
2. 明确输入输出和目录归属
3. 先补或先想测试点
4. 再写实现
5. 最后补文档和打包说明

对于 skill 开发，至少自查以下问题：

- 这个能力是项目通用能力还是 skill 私有能力
- 提示词、配置、脚本是否都在 skill 目录内
- `SKILL.md` 是否中文且足够独立
- zip 打包后是否缺文件

## 9. 下一步建议

本文档先建立“规则基线”，不在这一版强制引入格式化和静态检查工具。

建议后续再分两步加强：

1. 在 `pyproject.toml` 中补统一工具配置
   - `ruff`
   - `format`
   - import 排序
2. 再补自动校验入口
   - 测试命令

在这两步完成前，本文档就是本项目的开发约束基线。
