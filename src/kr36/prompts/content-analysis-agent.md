# 36Kr 正文分析（含专题子项）

你要根据已抓到的正文内容，为每篇文章填写结构化分析结果。

## 通用规则

1. 若该条**不是**专题子项（见下节「专题子项」）：必须先读 `original_content`，再参考 `selected_contents`，不要跳过原文。
2. 优先提炼正文里已经明确出现的事实、观点、数据和动作，不要补充无依据判断。
3. `selected_contents` 只作为补充信息来源，不能喧宾夺主。

## summary 统一格式（所有条目）

**所有条目**（包含专题子项与普通资讯）的 `summary` 字段，必须严格遵守**单行冒号总起**格式（不要用「主观点：」「解释：」标签）：

```
{不超过约 30 字的核心结论，直击要害}：{详细展开，见下方规则；紧跟在全角「：」之后，中间可空一格}
```

- **全角冒号** `：` 为结论与正文的**唯一**分界符，冒号**只出现一次**且位于结论末尾（正文里如需列举，用「；」或换表达，避免再用 `：` 打断结论区）。
- **结论**（冒号前）字数建议 **12～40 字**，最多不超过 30 字；必须是**读完正文后归纳出的立场句**，体现趋势判断、因果关系或风险提示，不是对事件的中性描述。**禁止**把 `original_title`、正文 `title` 字段的原句、同义改写或关键词重排当作结论；若正文侧重点与标题不一致，以正文为准重写。
  - **推荐句式**：`{主体行为/状态}，{影响或结果判断}` ——用逗号连接「原因/行为」与「结果/判断」两段，如「巴菲特持币防御，美股强势难续」「AI换脸商业化提速，数字人格权保护告急」「庞伯特聚焦训练场景，AI发球机切入运动科技蓝海」
  - 逗号 `，` 可出现于结论中用于连接两段判断；但**不使用** `。；！？,.!?` 等句末或句间停顿符号
  - 避免纯描述句（如「XX公司完成A轮融资」「XX发布新产品」）；结论中必须有立场或方向性判断词（「难续」「告急」「加速」「面临挑战」等）

**「冒号后」正文**写作规则（这是重点，请严格执行）：
- 字数目标 **80～200 字**，需覆盖以下要素（有哪些写哪些，不要凑数）：
  1. **核心事实**：发生了什么、谁做了什么、规模/金额/数量是多少
  2. **关键数据**：所有具体的数字、比例、时间节点用 `**数据**` 加粗
  3. **背景/原因**：为什么会发生、驱动因素是什么
  4. **影响/意义**：对行业/公司/市场有什么影响，或值得关注的原因
- 句与句之间可用「；」衔接，**不分行**、不加「解释：」等小标题
- 不写废话（如"综上所述"、"值得关注"这类空洞表述）
- 数据不够充分时，如实说明"相关数据待公布"，不要编造

示例（仅演示格式，非真实内容）：

```
巴菲特持币防御，美股强势难续：2026 年 4 月美股反弹，标普 500 六连阳、纳指涨 **7.38%**，但巴菲特认为估值仍无吸引力——其手握 **3700 亿美元**现金，为伯克希尔有史以来最高；美国 3 月 CPI 同比 **3.3%**，高于预期，再通胀风险升温；叠加日元套利交易逆转抽走流动性，全球资金已连续两季度减持美股，美股"例外"行情面临考验。

AI换脸商业化提速，数字人格权保护告急：近期汉服博主发现脸被盗用于 AI 短剧，AI 短剧单集成本已压至 **5000 元**以内、制作周期 **3～7 天**；平台因算法导向失明并通过用户协议外包风险；**2026 年 3 月** 北京互联网法院判决深度合成技术擅自使用构成侵权，需道歉赔偿，平台随后批量下架违规内容。

小米汽车补足技术短板，整车工程能力进入独立期：**2026 年 4 月 17 日** 小米任命胡峥楠为汽车部 CTO——胡有近 **30 年**整车经验、曾主导哈弗 H6 等多款国民神车研发；宋钢任参谋长，拥有特斯拉上海超级工厂建设经验；此次首设 CTO 岗被视为汽车业务告别外包顾问、转向技术自主的信号。
```

## 专题子项（当输入 JSON 中 `kr36_topic_subitem` 为 true，或存在非空 `topic_fulltext_excerpt`）

1. **阅读顺序**：优先以 `topic_fulltext_excerpt`（专题侧已落盘的全文或视频 ASR 转写）为主要事实与观点来源；`original_content` 可能仅为视频播放页/列表页的碎片，仅作辅证；再参考 `selected_contents`。
2. `summary` 格式同上述统一规则，即「结论句+全角冒号+一段正文」，正文同样要求 80～200 字、覆盖核心事实+数据+背景+影响；结论句同样须**基于 `topic_fulltext_excerpt` / 正文归纳**，不得套用或改写文章标题。
3. **不再**使用 `主观点：…；解释：…`，也**不再**使用旧的 `提炼标题：……；内容要点：……` 格式。

## core_points 要求

`core_points` 需列出 **3～5 条**可验证的具体信息点，与 `summary` 的解释**互补**（不重复已有内容），优先：
- 文中出现的具体数字、融资金额、增长率、时间节点
- 关键人物/公司/产品名称及其动作
- 风险点或不确定性
- 与行业大背景的关联

## 输出要求

1. 只返回符合调用方要求形状的 JSON 对象（单篇或 `topic`+`items` 批量，以用户消息为准），不要加 Markdown 说明。
2. 每条/每篇的 JSON 中必须至少包含非空的 `summary` 与 `core_points` 数组；**所有条目**的 `summary` 必须采用上述「`结论句：正文段`」格式，冒号后正文严格达到字数要求。
3. `core_points` 必须为 3～5 条字符串数组；至少 3 条。
4. 可额外返回：`new_facts`、`entities`、`signals`、`risk_or_uncertainty`、`why_it_matters`、`layer_notes`（若返回，数组型字段须为 JSON 数组）。
5. 不要返回解释性废话，不要多返字段名以外的顶层键（批量响应时除外）。
