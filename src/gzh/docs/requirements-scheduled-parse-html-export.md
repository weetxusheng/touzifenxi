# 需求文档：定时解析公众号文章、留痕并生成 HTML

**版本：** 2026-05-18 v0.8（草案）  
**状态：** 待评审  

**变更 v0.2：** 必选补充「正文图片及关联资源信息的同步解析」（见 §4.2.1）。  
**变更 v0.3：** 明确抓取产物与解析成品的目录层级为 **`根目录/<日期>/<公众号>/`**（见 §4.0）。  
**变更 v0.4：** 必选补充「内容四维度解析」：**事实、背景、产生的影响、反面观点**（见 §4.2.2）。  
**变更 v0.5：** 明确 **「留痕」为全流程逐步留痕**（含 **API 请求与返回体** 等），并以 **JSON 文件** 作为留痕信息主存储（见 §5）。  
**变更 v0.6：** **留痕粒度下「单体聚合 JSON」**（单次任务全部 `steps` 入同一文件，无侧车拆文件），见 §5.2～§5.3。  
**变更 v0.7：** 解析按 **`公众号 + 日期`** 分区：**该目录内多条抓取 `.html` 汇总为唯一成品 `<成品文件名>.html`**（不做「一数源一数成品」）。  
**变更 v0.8：** 抓取与解析均为**定时任务**，在产品上构成 **「抓取 → 解析」端到端日批流水线**（可有时间窗，如凌晨抓、早高峰后解析，见 §4.3）。

## 1. 背景与目标

在已有「通过大佳啦 API 抓取公众号文章并导出 HTML」能力（入口：`run_dajiala_export.bat` 或 `python -m gzh_pipeline.cli.fetch` / `gzh-fetch`）的基础上，建立 **定时抓取 →（约定间隔后）→ 定时解析** 的 **一整套日批流水线**，共享同一套 **`<业务日>/<公众号>`** 目录约定（§4.0），便于运维按时间表编排（示例见 §4.3）。

1. **定时抓取**：按计划的 **抓取任务** 将当日/指定业务日的多篇 `.html` 写入 **`exports/<日期>/<公众号>/`**（抓取通过 **Windows 任务计划 / cron** 或等价调度触发，见 §4.3）；  
2. **定时解析**：在抓取落盘完成后、由**另一计划时刻**触发的 **聚合解析任务** 读取上述目录，生成 **唯一**成品 `.html` 与 §5 所规定之 **聚合 `.trace.json`**（§4.1～§5）；两段之间允许 **固定时间窗**（例：凌晨 6:00 抓、8:00 解析），不要求同一进程内串行，但须满足 §4.3 **衔接约定**；  
3. **留痕**：对**每一步可观测操作**写入可追溯记录（含 **对外 API 请求与其返回数据**、文件读写、解析/模型调用等），**主存储为 UTF-8 JSON 文件**（见 §5）；抓取链路与解析链路均须落痕，且可通过 **`biz_date`、路径、`run_id`** 关联到同一业务日；  
4. **聚合产出**：对每个 **`YYYY-MM-DD` + 公众号** 抓取目录执行 **一次**聚合解析，生成 **唯一**规范的 **`.html` 成品**（见 §4.0（2）、§4.1），写入 **`PARSE_OUTPUT_ROOT/<同一日期>/<同一公众号>/`**；成品中须有 **§4.2.2** 针对**当日抓取集合整体**的四维度拆解；图片均须按 §4.2.1 处理并留痕。

在已有能力基础上，**产品视角上**须将 **「定时抓取」与「定时解析」** 视为 **同一条日批业务链路**（非彼此无关的两个脚本），衔接关系、空目录/失败重试与告警在 §4.3、§8 约定。

**非目标（本迭代默认不做，除非产品线确认）：**

- 替代大佳啦抓取链路或绕过 API 直连微信；
- 通用 CMS 入库、向量检索等非 HTML 投递形态（可作后续扩展）。

## 2. 名词说明

| 名词 | 说明 |
|------|------|
| **端到端日批流水线** | **定时抓取作业** 产出某 `业务日/公众号` 下多篇源 `.html` → 经约定时间窗后 **定时聚合解析作业** 读入同一路径键、产出单品总结 `.html`；两段共享目录约定，在运维上可配置为两个触发时刻（§4.3） |
| 原始抓取 | 按 §4.0（1）：**同一 `YYYY-MM-DD` / 同一公众号目录下可有 N 篇**抓取产生的多个 `.html`（由 **定时抓取任务** 写入） |
| **聚合解析任务** | 以 **`(业务日, 公众号)`** 为调度单元：将该目录（或等价列表）内的**全部**抓取 `.html` 作为输入集，产出 **一则**聚合成品 `.html` 与 §5 **一则**聚合审计 JSON |
| 解析 | 对**当日该号抓取集合**做汇总加工：跨文件抽取信息、归因到各文章来源块，并形成 **§4.2.2 四维度的综合归纳** |
| 维度解析输出 | **事实 / 背景 / 产生的影响 / 反面观点** 四套内容针对**该日该号抓取集合整体**的综合表述（仍可脚注各条来源标题或链接）；须在成品 HTML 与 `summary`/留痕字段中可核对 |
| 留痕（逐步留痕） | 对流水线**每一步**落盘；**解析侧：** **一次聚合任务（同 `YYYY-MM-DD` + 同公众号输入集）→ 恰好一个聚合 `.trace.json`**，内嵌全部 `steps`（§5.2）；**抓取导出侧：** 粒度可仍为「单次导出链路」单体 JSON（可与解析不同，见 §10） |
| 成品 HTML | **每个 `日期/公众号`** 聚合任务产出 **恰好一个** `.html`，内容含当日各源合集（§4.0（2）、§4.2） |
| 图片信息 | 正文中每张图片的稳定 URL（或本地化路径）、占位属性（如懒加载）、顺序、可选 `alt`/`title`/`data-*`（若源中存在）；用于留痕或与正文对齐校验 |

## 3. 用户场景

1. **运营/编辑**：系统在夜间/早间先 **定时抓取**，再在上班前完成 **定时解析**；用户打开 **单日单号一份**汇总 `.html`，先读 **四维度**，再展开各文章来源；
2. **开发/运维**：某次聚合解析异常时，能根据 **`(日期, 公众号)`** 对应的 **单笔 `.trace.json`** 与各 `steps` 定位是哪个源 `.html`、哪次接口或模型调用失败；
3. **合规审计**：可调出某日某批次「输入 → 输出」对应关系及处理结果。

## 4. 功能需求

### 4.0 路径与目录约定（必选）

以下约定用于**抓取落盘**与**解析产出**两边对齐，便于按日、按公众号检索与留痕对上号。

**（1）公众号抓取文章的保存路径（默认抓取根目录名 `exports/`）**

`exports/<YYYY-MM-DD>/<公众号安全目录名>/<文章文件名>.html`

| 段位 | 说明 |
|------|------|
| `exports/` | 抓取产出根目录；实现上可与 CLI `--output-dir` 对应，默认仍建议为仓库内 `exports` |
| `<YYYY-MM-DD>` | **业务日**（与抓取任务所认领的刊发日或抓取日一致），格式固定为 **ISO 日期** `YYYY-MM-DD`；所用**时区**（本地日 vs UTC）在技术方案或运维手册中明确 |
| `<公众号安全目录名>` | 与现有文件名安全策略一致的安全化公众号名（可与 `safe_filename(account)` 规则对齐） |
| `<文章文件名>.html` | 单篇文章一个 UTF-8 HTML 文件，basename 须经安全化处理，避免穿透路径 |

**（2）解析生成的 `.html` 保存路径（可配置解析根目录）（单日单号一单成品）**

`<PARSE_OUTPUT_ROOT>/<YYYY-MM-DD>/<公众号安全目录名>/<成品文件名>.html`

| 段位 | 说明 |
|------|------|
| `<PARSE_OUTPUT_ROOT>` | 环境变量或配置中的**解析产出根目录**（示例：`parsed_exports/`），可与 `exports/` 分立 |
| `<YYYY-MM-DD>`、`<公众号安全目录名>` | 与抓取侧**同源两级目录**对齐；一次解析任务即以该 **`日期 + 公众号`** 为主键加载其下全部源 `.html` |
| `<成品文件名>.html` | **与同目录抓取文件数量解耦**：例 `exports/2026-05-18/证券时报/` 下 **6** 个抓取文件 → `parsed_exports/2026-05-18/证券时报/` **仅产出 1 个** `<成品文件名>.html`。文件名由配置/模板定型（示例：`daily.html`、`{公众号}_{日期}.html`），并写入留痕 `output_path` |

- **条目关系：** 抓取侧为「同一目录多篇 `.html`」；解析侧为「同一 `日期/公众号` 目录**对应唯一成品 `.html`**」。禁止「抓取 N 个文件 ⇒ 自动生成 N 个成品 `.html`」的一一对应。

若采用 §4.2.1 的**本地镜像**策略，静态资源目录与 **唯一成品**同窗，建议：

`<PARSE_OUTPUT_ROOT>/<YYYY-MM-DD>/<公众号安全目录名>/assets/`（文件名防冲突策略见技术方案）。

### 4.1 输入来源

- **主路径：** 在 **`PARSE_INPUT_ROOT`**（默认与抓取根一致）下定位 **`抓取根/<YYYY-MM-DD>/<公众号>/`**，收集该目录下全部 **`*.html`**。
- **调度粒度（必选）：** 一次解析作业的输入为该目录内当时存在的抓取文件集合（可配置排序，如文件名或 mtime）；**同一作业只生成 §4.0（2）规定的单个成品**。不得默认采用「每条源 `.html` 对应一条独立成品 `.html`」的模式。
- **`日期`、`公众号`** 可由相对路径推导，并写入留痕（见 §5，可增 `biz_date`、`account_dir` 等字段）。
- **扩展（可选）：** 从清单文件（CSV/JSONL）读取待处理条目：`源路径`、`原文 URL`、`抓取时间`、`账号名`（路径仍需满足或可映射到 §4.0）。
- **待确认：** 是否只处理「上一轮抓取新增的」文件（见 4.4 增量与幂等）。

### 4.2 解析内容

对每个 **`(YYYY-MM-DD, 公众号)` 聚合批次**，在完成**跨源汇总**的前提下，须在**唯一成品 HTML** 与 **§5 summary**（及 `steps` 内各源拆解）中体现：

- **各文章来源块**（必选）：每一原始抓取 `.html` 须在成品中以可区分的小节呈现（标题/链接摘自源或使用源文件名与安全标题），并保持各文 **正文与原图顺序**可与源对照（细则 §4.2.1）
- **公号级汇总元数据：** `公众号`、`业务日`、`源文件清单`（有序列表：`相对路径`、`sha256` 可选）、`源篇数`

对**每一源 `.html`** 在流水线内部仍需抽取（不要求单独落盘）：**标题 / 正文 / 图 / 原文链接**（若有）等以便汇总；语义四维度针对**当日合集整体**产出（§4.2.2）。

- **内容四维度**（必选）：**事实、背景、产生的影响、反面观点**（§4.2.2，**基于当日该号全部源文**的综合归纳）

- **可选：** 发布时间、作者、摘要、封面图 URL（能从各源中提取则列入对应来源块）

**解析规则（结构层）：** 初始实现可先针对现有 `wrap_html()` 包装的页面结构或大佳啦返回体中的常见外层标签做稳定选择器；后续若正文结构多变，再通过配置或小范围规则插件扩展。**需在实现前冻结「源文档类型」枚举**（例如：仅「本仓库脚本导出的 wrapped HTML」）。

**解析规则（语义层 / 四维度）：** 须单独约定实现手段（规则模板、提示词 + 模型、或人机混合），并固定 **输出语言、是否必须引用原文片段、空维度的标准表述**；无论采用何种手段，**禁止无依据编造**（见 §4.2.2）。

### 4.2.1 正文图片与资源信息的同步解析（必选）

公众号 HTML 常以图片承载核心信息（截图、配图、图表等），解析流水线**不得丢图、不得在无记录的情况下静默丢弃「无法处理的图」**。需满足：

1. **穷尽扫描正文 DOM**中所有与图片相关的节点，包括但不限于：`<img>` 的 `src` / `data-src` / `data-original`（及同类懒加载占位属性）、`<picture>`/`source`、`background-image`（若出现在正文区域内且可作为关键内容来源，**待方案阶段**判断是否纳入首期）、以及微信侧常用的 `iframe`/第三方组件中的可解析图片嵌套（**能解析则必选，不能解析须在留痕中记 `partial`/`unsupported` 与原因**）。

2. **图片信息数据结构（逻辑要求，存储形态可实现在 JSON/HTML 任一环节）：**
   - 在正文中的 **阅读顺序序号**；
   - **解析选用的最终访问 URL**（多属性并存时须有明确优先级并在留痕或可配置文档中写明）；
   - **`alt` / `title`（若有）**；
   - **原始属性快照（推荐）：** 关键 `data-*` 或自定义属性中与防盗链、尺寸有关的字段，便于问题复现；
   - **可选：** 宽高、MIME/扩展名推断、下载后的本地校验哈希（若走本地化策略）。

3. **成品 HTML 中的呈现：** 成品正文中的图片占位与顺序必须与解析结果一致；**URL 重写策略待定二选一默认（评审确定）：**
   - **A 保留远端 URL：** 改写为统一可用的 `src`（合并懒加载到实际地址），尽量不破坏微信侧参数；离线打开可能受防盗链/时效影响 → 须在风险与运维中接纳或配合浏览器策略。
   - **B 本地镜像：** 将图片下载到 §4.0（2）的 **`assets/`** 目录（与唯一成品同窗），文件名须可区分归属源 `.html` 与图序（示例：`<源文件安全 stem>__img_<n>.<ext>`）；成品 HTML 使用**相对路径**引用；下载失败须在 `steps`/留痕中说明，并在成品内保留可读占位与原 URL。

4. **与原抓取文件的关系：** 若源 HTML 中图片已为可访问外链，仍以「解析阶段的扫描结果」为准写入留痕（避免仅依赖编辑器肉眼核对）。

**与本节相关的风险：** 微信/中间页图片 URL **带时效或防盗链**；本地化需控制并发、磁盘与合规（仅下载文章范围资源）。要求在技术方案中明确 **防盗链/Headers、超时、重试、最大单图体积与总配额**。

### 4.2.2 内容四维度解析（必选）

对 **指定业务日 + 指定公众号** 目录下**当日抓取集合整体**，在四维度区块中给出**综合归纳**（非按源文件各做四套维度），便于速读当日要闻与争议点；脚注或列表中应可追溯至 **具体文章来源**（文件名或原标题）。

维度含义仍以**当日全部收录正文**为证据边界：

| 维度 | 含义（写作指引） |
|------|------------------|
| **事实** | 当日各文可核对的**客观信息**归纳：时间、主体、数据、事件经过、引述等；逐条时建议标注**来自哪一条源**（短引或定位说明） |
| **背景** | 综合理解当日稿件所需的**情境与前因**（可跨文合并），避免与单文背景混淆时在句末注明来源 |
| **产生的影响** | 当日内容中讨论或暗示的**影响、后果、意义、趋势**之汇总；推测须标为推断 |
| **反面观点** | **所有源文合集中**明确出现的对立视角、异议、风险提示等之汇总；若**全部源文均未涉及**反面观点，本维度**不得虚构**，须标准占位 + 理由，并记 `dimensions_coverage` |

**硬性要求**

1. **四维度齐备：** 成品中四个区块均需存在对应标题或小节 ID（锚点稳定、`id`/标题文案在实施时冻结），内容上允许某维列为空，但必须带**可见的「暂无 / 不适用」说明 + 简述理由**。
2. **忠于原文：** 不得在「反面观点」「影响」等处**增补原文没有的立场**；可做合并归纳，但须可复核。
3. **与全文正文的关系：** 建议成品 HTML **先呈现四维度摘要区（当日合集级）**，再按 **§4.2 各文章来源块** 展开各文全文（或折叠）；版式在实施阶段定稿；**仍仅输出 §4.0（2）所规定的那一个成品文件**。
4. **实现手段开放：** 允许规则 + 分类器、或可审计的生成式模型；若使用模型，留痕必须记录 **`dimension_engine`**（或 `dimension_model` / `dimension_prompt_revision` 等等价字段）、版本与快照标识，并与 §5 表字段对齐，便于回放。

**与该节配套的测试：** Golden 集：**同一目录多源 `.html` + 人工标注的合集级四维度期望**，用于回归「跨文不串维、不无依据反面观点」。

### 4.3 定时执行与「抓取 → 解析」端到端编排（必选）

- **整体定位：** **抓取** 与 **解析** 均为 **定时触发的独立作业**（典型：操作系统 **任务计划程序 / cron** 调 `run_dajiala_export.*`、`parse_aggregate.*` 等），但在需求上属于 **同一条业务流水线**：先落 **`exports/…`**，再读同键写 **`parsed_exports/…`**。允许 **不同时刻**（例：**06:00 抓、08:00 解析**），不要求同一脚本内顺序 `fork`/`wait`，但必须通过 **时间窗 + 目录约定** 保证解析读到的是 **当日批次**（或方案规定的业务日）。
- **抓取定时：** 须写清 **触发频率、cron 表达式、所用 `EXPORT_ROOT`/`--date`**；抓取结束须在 **`EXPORT_AUDIT_JSON_ROOT`**（若已启用）与 **`exports/<biz_date>/<公众号>/`** 体现**可追溯**结果。
- **解析定时：** 须晚于抓取完成后的**安全间隔**（可配置 `PARSE_MIN_DELAY_AFTER_FETCH_MINUTES` 或由运维保证 **解析 cron 晚于抓取 cron ≥ N 分钟**）；解析入口须指定 **`PARSE_INPUT_ROOT` ≥ 抓取写出目录**、以及待处理的 **`biz_date` 列表**（或「扫描昨日/今日目录」策略，在实施清单冻结）。
- **衔接与失败：** 若解析触发时对应 `exports/<日>/<号>/` **为空或抓取任务失败**：解析作业须 **显式留痕**（`skipped`/`failed` 原因）、可选 **告警**（§9），**禁止**静默覆盖旧成品导致误判成功。若抓取仍在进行、目录未稳定：**不建议**与解析时间窗重叠；若重叠，以实现层 **文件锁/完成标记 `.done`**（待定）或纯运维错开时段解决。
- **编排实现（二选一即可）：** **A)** 两个独立计划任务 + 文档化时刻表；**B)** 统一调度器/父脚本异步：`抓取 && sleep/wait && 解析`。**不允许**仅口头约定而无运维侧可见的配置。

- **原补充策略（仍适用）：** **低频轮询**解析（每 N 分钟扫描是否有新 `exports`）可作为变体，但须仍满足 **聚合粒度** 与 **幂等键**（§4.4）。
- 单次运行应可在合理时间内结束，并具备**超时与单文件失败不拖死整批**的行为（见 4.6）。

### 4.4 增量与幂等（留痕要强依赖）

- 聚合任务幂等键建议为：**`biz_date` + `account_dir` + 输入集合指纹**（如对目录内各源 `.html` 路径排序后拼接各文件 **`source_sha256`** 再求总哈希）+ **`parse_version`**。同一指纹且已成功、无 **`--force`** 时可跳过重复生成。
- **待确认：** 是否需要 `--force` 或「按批次号全量重跑」。
- **输出命名与路径：** 成品须落在 **`<PARSE_OUTPUT_ROOT>/<YYYY-MM-DD>/<公众号>/`** 下（§4.0（2）），**恒定单文件**；`<成品文件名>` 由 **`PARSE_AGGREGATE_OUTPUT_STEM`** 或模板配置（见 §6），须写入留痕 `output_path`。

### 4.5 成品 HTML

- **格式：** UTF-8，`.html` 单文件；可内联必要样式或引用固定公共样式（待定）。
- **模板：** 统一页头页脚或元数据区块（可选），至少包含：`title`、`meta charset`、可追溯的 **`data-*` 或 HTML 注释**（批次 id、解析时间、解析器版本、**§4.2.2 维度解析器版本标识**）。
- **四维度区（必选）：** 须有独立可读区块，自上而下建议顺序：**事实 → 背景 → 产生的影响 → 反面观点**；每区带 **稳定小节标题**（与 §4.2.2 表一致）、建议提供 **HTML `id`**（如 `dim-facts`、`dim-background`、`dim-impact`、`dim-counterpoints` ，具体命名在技术方案冻结），便于程序化抽查与书签。
- **全文正文区：** **按源 `.html` 分块**：每一抓取文件对应成品中一节（或小标题 + 锚点），内嵌该源清洗后正文及 §4.2.1 图片；可加 **目录（TOC）** 链到各文章来源块。
- **图片：** 成品正文中保留与 §4.2.1 一致的图片结构与可访问引用（远端 URL 或相对路径镜像二选一已定稿）。
- **目录布局：** **必选** §4.0（2）：**解析根 `<PARSE_OUTPUT_ROOT>` + 与抓取侧相同的 `<日期>/<公众号>/`**；若采用本地镜像，在同窗下挂载 **`assets/`**（参见 §4.0）。

### 4.6 错误处理

- **单源读取失败：** 某一 `.html` 读失败或畸形时：在 `steps` 与 **`summary.partial_sources`** 记原因；**其余源继续**参与汇总；仅在**全部源**不可用时将整聚合任务判 **`failed`**。
- **正文可解析但部分图片不可用**（远端 403、超时、超限）：记 **`partial`** 或等价策略，`image_failures` 必填项级说明；不得在无可达 `src` 的情况下假装成功。
- **四维度异常：** 无法在成品中按要求输出四个带标题/锚点的小节（含「明确空」占位）或引擎异常退出时，记 **`failed`** 或由 `dimensions_coverage` 逐项标 `failed`；禁止生成「貌似四维度齐备」但实际缺节、或反面观点无理由填充的内容。
- **与留痕的配合：** 任一失败或 `partial` 须在对应 **JSON 留痕**的 `steps` 中体现**最后出错步骤**及错误对象，不得仅写控制台日志而无文件留痕。

## 5. 留痕需求（可追溯）

### 5.1 原则：逐步留痕（非仅结果汇总）

「留痕」指对流水线中**每一步可复现、可审计的操作**均写入留痕，包括但不限于：

| 步骤类型（示例） | 须记录的内容要点 |
|------------------|------------------|
| **HTTP/API 调用**（如大佳啦 `monitor/*`、`search/*`，或模型供应商 API） | **请求**：`method`、`url`、**脱敏后的 headers**、请求体 `body`；**响应**：`status_code`、耗时、**响应体**；超字节上限时按 §5.3 **在同一则 `.trace.json` 内截断摘要**。**禁止**再拆并列 JSON/HTML 侧车文件 |
| **图片拉取**（GET 单张图） | 请求 URL（可截断 query 显示策略）、状态码、字节数或落盘路径、`sha256`（可选） |
| **本地文件** | 读取/写入路径、编码、`byte_length` 或 `sha256`（按需） |
| **解析子阶段**（DOM 抽取、四维度生成前后） | 阶段名、输入摘要（如首节 N 字符哈希）、输出摘要或中间结构大小；若经 LLM，须另记 **完整请求/响应** 或等价可回放字段（与 API 行同类） |
| **跳过/幂等** | 跳过原因、匹配的上一留痕 `run_id` 或 `source_sha256` |

**抓取侧**（`gzh_pipeline`/计划任务调 `run_dajiala_export.bat` 等）与**解析侧**凡发生对外网络请求，均须按上表对 **每一次** 请求×响应落痕，**不得**合并多跳为一条无法还原的单条日志。

### 5.2 JSON 文件存储（主介质，必选）

#### 硬性规则：**一次聚合解析任务 → 恰好一个聚合 `.trace.json`（解析侧）**

- **解析侧必选：** 每一个 **`(biz_date, 公众号)` 聚合任务**（输入为该目录下 **0…N** 个源 `.html` 的集合）产出 **唯一一个 UTF-8 JSON**，内含该任务 **全部** `steps`（含逐源 `file_read`、逐图拉取、跨源汇总、四维度引擎调用等）。**禁止**将同一聚合任务拆成多个并列 `.trace.json`。  
- **与成品对应关系：** **1 个聚合任务 ⇒ 1 个成品 `.html`（§4.0）⇒ 1 个 `.trace.json`**。  
- **批次索引（可选）：** `<AUDIT_JSON_ROOT>/<run_id>/run.json` 仅存批次元数据及本批各 **聚合 `.trace.json` 路径列表**；`run.json` **不得**承载任一聚合任务的 `steps`。  
- **建议文件名：** `<AUDIT_JSON_ROOT>/<run_id>/<biz_date>_<account_slug>.trace.json`（**不再使用单篇 `article_slug`**）。

**抓取导出侧：** 仍可沿用「**单次抓取导出链路 ⇒ 一单 JSON**」粒度（可能与解析侧语义不同）；若一次导出为多篇文章拉取 HTML，在技术方案中说明该 JSON 表征的是抓取批次还是单单篇导出。

- 留痕信息**以 UTF-8 编码的 `.json` 文件**为主存储；**不**以「仅数据库、仅控制台」代替文件落盘。
- **可配置根目录：** **`PARSE_AUDIT_JSON_ROOT`**（解析侧）、对称 **`EXPORT_AUDIT_JSON_ROOT`**（抓取导出侧）。

`account_slug` 与 §4.0 路径安全规则一致，避免路径注入。

### 5.3 大报文与密钥（单文件约束下）

- **不超上限时：** `steps[].detail.response.body`（及对称 request body）应尽量 **完整内联**，便于单次打开即审计。
- **超过 `AUDIT_STEP_BODY_MAX_BYTES`（可配置）时：** **仍在同一则 `.trace.json` 内**截断摘要……**禁止**……**侧车**（违者视为不满足「一聚合任务一单 JSON」）。
- **严禁**在 JSON 中写入明文 **`api_key`、`access_token`、`Authorization`、cookie** 等；请求/响应中涉密字段须 **统一脱敏**（如替换为 `***` 或哈希占位），脱敏规则在实施清单中冻结。

### 5.4 `steps` 数组条目建议形态（示例）

单步留痕为 JSON 对象，**最小**宜包含：`step_index`、`ts`（ISO8601）、`kind`（如 `http_request`、`file_read`、`dimension_infer`）、`ok`（bool）、`error`（可选）、`detail`。其中 **`http_request` 类**建议显式包含：

```json
{
  "step_index": 3,
  "ts": "2026-05-18T10:11:12+08:00",
  "kind": "http_request",
  "label": "dajiala_post_history_page1",
  "ok": true,
  "detail": {
    "request": {
      "method": "POST",
      "url": "https://www.dajiala.com/fbmain/monitor/v3/post_history",
      "headers": { "Content-Type": "application/x-www-form-urlencoded" },
      "body": { "key": "***", "url": "gh_xxxx", "page": 1 }
    },
    "response": {
      "status_code": 200,
      "elapsed_ms": 420,
      "body": { "code": 0, "data": { "list": [ "..." ] } }
    }
  }
}
```

（上例中 `body.key` 已为脱敏占位；真实文件须与脱敏策略一致。）

### 5.5 摘要字段（冗余在 `summary` 中便于检索）

除 `steps` 外，**聚合任务** JSON 顶层 **`summary`** 建议包含：

| 字段概念 | 说明 |
|----------|------|
| `run_id` / `batch_id` | 隶属批次 |
| `source_paths`（数组） | 参与汇总的各源 `.html` 相对或绝对路径（有序） |
| `source_count` | 源文件数 |
| `input_bundle_sha256`（推荐） | 输入集合内容指纹（用于幂等，见 §4.4） |
| `account`、`biz_date`、`output_path` | §4.0 |
| `parse_version`、`dimension_engine`、`status`、`dimensions_coverage` | 语义与配图、四维度 §4.2 |
| `partial_sources`（可选） | 读取失败或跳过的源及原因 |
| `image_count_*`、`image_failures`、`error_message` | 全集统计或分源明细（实现二选一并在技术方案写明） |

**留存周期（待确认）：** 按 **run_id** 分目录轮转或按磁盘配额清理；是否与成品、`exports` 同框备份。

## 6. 配置与运维

- **配置文件或环境变量**（示例，名称可调整）：  
  - `EXPORT_ROOT` 或等价项：抓取根目录，默认 `exports/`；其子结构须为 **`/<YYYY-MM-DD>/<公众号>/`**
  - `PARSE_INPUT_ROOT`：解析扫描起点，通常等于 `EXPORT_ROOT` 或与之一致的可配置路径  
  - `PARSE_OUTPUT_ROOT`：解析成品根目录；其子结构须与抓取侧对齐 **`/<YYYY-MM-DD>/<公众号>/`**
  - `PARSE_ASSETS_SUBDIR`（可选）：本地化图片子目录名，默认 `assets`  
  - `PARSE_IMAGE_MODE`（可选）：`remote`（保留远端） / `mirror`（下载镜像），默认待评审选定  
  - **`PARSE_AUDIT_JSON_ROOT`（必选）**：解析侧 **§5 JSON 留痕根目录**，其下按 `run_id/` 分批存储 `run.json` 与 `.trace.json`  
  - **`EXPORT_AUDIT_JSON_ROOT`（必选，抓取侧）**：对大佳啦等 **每一步 API** 写入 §5 同等结构的 UTF-8 JSON（可与解析根分立，也可与 `PARSE_AUDIT_JSON_ROOT` 共用基目录但以子路径区分）  
  - **`AUDIT_STEP_BODY_MAX_BYTES`（可选）**：单步内嵌 body 的建议上限（字节）；超过则在**同一则** `.trace.json` 内按 §5.3 **截断摘要**，不产生侧车文件  
  - **`PARSE_AGGREGATE_OUTPUT_STEM`** 或等价模板：**`<成品文件名>`**（不带 `.html`），如 `daily`、`证券时报_合集`（与 §4.0（2）一致）  
  - `PARSE_DIMENSION_*`（可选）：维度解析引擎相关配置占位，具体键名在技术方案对齐 §4.2.2  

- **定时与编排（建议写入运维手册或 `.env`）：**  
  - `FETCH_SCHEDULE` / `PARSE_SCHEDULE`：人类可读的 cron 或「每日 HH:mm」说明（与 §4.3 一致）  
  - `PARSE_MIN_DELAY_AFTER_FETCH_MINUTES`（可选）：解析须晚于抓取的**最少间隔**（分钟），用于校验或告警  
  - `PIPELINE_BUSINESS_DAY`（可选）：解析默认处理的 **`biz_date`**（如 `yesterday` / `today` / 显式 `YYYY-MM-DD`），须与抓取任务写入的日期一致  

- **CLI 建议：** `python -m gzh_pipeline.cli.parse …` / `gzh-parse` 支持按 **`日期/公众号`** 聚合；抓取侧通过 `run_dajiala_export.bat` 或 `python -m gzh_pipeline.cli.fetch` 由计划任务触发，**时刻须早于**解析任务（§4.3）。
- **日志：** 控制台 + 轮转文件；`ERROR` 记录到 **具体聚合任务**或失败源文件名

## 7. 验收标准（建议）

1. **聚合产出：** `exports/<日期>/<公众号>/` 下存在 **N（N≥1）** 个源 `.html` 时，**同一路径键**在 `PARSE_OUTPUT_ROOT` 下**仅生成 1 个**成品 `.html`（§4.0（2）），内含 **§4.2.2 合集级四维度** + **按源分块的全文**；`N=6 ⇒ 1` 等场景必须满足。  
2. **四维度：** 成品含针对**当日该号全部源文**综合归纳的四类区块，规则见 §4.2.2。  
3. **图文：** 各文章来源块内图片与对应源 HTML 一致或可解释失败；**全集**图片问题在 `summary`/`steps` 可追溯。  
4. **端到端编排：** 文档或配置中可还原 **抓取时刻表** 与 **解析时刻表** 及 **`biz_date` 对齐规则**；抽检 **06:00→08:00** 类场景下解析读到的 `exports/…` 即为抓取批次（可通过 `summary`/`run` 时间戳交叉验证）。  
5. **留痕 JSON：** **`run.json` 可选**；**每一 `(日期, 公众号)` 聚合任务恰好一个** `<biz_date>_<account>.trace.json`**，**`steps`** 覆盖读入各源、网络调用与汇总全过程；**请求+响应**内联或 §5.3 截断，无侧车。`summary.source_paths` 与源目录列表一致。
6. **幂等：** §4.4 聚合指纹：`--force` 外同指纹不重跑。
7. **隔离：** 不修改 `exports/` 下当日该号抓取原文件。
8. **测试：** Golden：**多源 → 单品**；断言 **产出 HTML 数量为 1**、**审计 JSON 为 1**/任务；mock HTTP **请求+响应**均写入同一 `.trace.json`；脱敏与部分源失败续跑逻辑。

## 8. 依赖与风险

- **调度与时钟：** 抓取/解析 **cron 配错、时区不一致、夏令时** 等导致「解析早于抓取」或读到空目录 → 须 **告警 + 留痕 `skipped`**；关键环境统一 **同一时区**（见 §4.3）。
- **语义归类风险：** 「事实 vs 推断 vs 反面观点」存在主观边界 → 须有 **版本化的规则/模型**、`dimension_warnings` 与抽检流程；对用户展示可加「机器生成，仅供参考」类声明（文案由法务/运营定）。
- **正文结构漂移：** 大佳啦或微信平台侧 HTML 结构变化会导致解析失效 → 需 **`parse_version` 升降级 + 告警**。
- **图片 URL 时效与防盗链：** 外链图片可能不可用 → 须在 **mirror 模式**或可接受的 **remote + 告警**策略中选型；本地化需控制带宽与失败 visibility。
- **留痕磁盘与隐私：** 单体 `.trace.json` 可能体积较大 → §5.3 **字节上限与截断策略**必选；归档目录需权限控制并遵守留存策略。
- **多端合并复杂度：** 同日多源合并为单 HTML 与单 trace，**归因与排序规则**（TOC、失败源）须在实现中固定，避免编排歧义。
- **安全：** 全文 **API 留痕**须经 **密钥脱敏**（§5.3）；响应体可能含个人信息或可复制链接 → **访问控制与留存周期**须与法务一致；成品 HTML 内链需考虑是否仅允许 `https`。

## 9. 待定问题清单（评审用）

1. 输入是否**仅**为当前导出格式，还是需要兼容历史手工保存的 HTML？  
2. **（已定）目录：** 抓取与解析可使用两个不同「根」，但下级相对路径必须为 **`<YYYY-MM-DD>/<公众号>/`**；若要放在同一棵树（如 `exports/parsed/`），也不得省略或调换这两级层级。  
3. **（已定）编排：** **定时抓取** 与 **定时解析** 为 **同一条日批流水线** 的前后两环（允许不同时刻触发，例 6:00 / 8:00），目录与 `biz_date` 须对齐（§4.3）。  
4. 定时频率与「只处理某日」：**按文件名时间、mtime、还是抓取清单**？  
5. **（已定）留痕介质：** UTF-8 JSON（§5.2）；解析侧 **「一聚合任务一单 `.trace.json`」**：即 **同一 `日期/公众号`、一次汇总作业**对应 **唯一**审计文件（全流程 `steps`）；`run.json` 仅可选批次索引。**≠**「每个抓取源 `.html` 各生成一个 `.trace.json`」。若需 SQL 检索可另建索引库（可选）。
6. 是否需要 Webhook/邮件在**批次部分失败时告警**？  
7. 图片交付策略：**默认 `remote` 还是 `mirror`**？本地化是否需统一转码/WebP（一般默认否）？  
8. 四维度解析：**纯规则/pipeline**，还是 **可调用的生成式模型**？输出语言是否固定为简体中文？是否需要 **逐条带出原文小节编号/短引用**（强审计）？
